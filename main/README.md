# Orchestrator Suite 3.0.3

[English](README.en.md) · [版本记录](CHANGELOG.md) · [发布说明](docs/RELEASE-NOTES-3.0.3.md)

DeepSeek Harness（DSH）的编排提示套件：编排看板、紧凑进度状态栏，以及套件自建的**调度编排模式**。模型先报告对任务与能力的理解，再执行；用户可通过阶段框图、步骤、理解和实际证据定位问题。它提供引导，不替其他插件审批工具或决定项目技术方案。

## 两种使用范围

| 当前 Agent 预设 | 套件行为 |
| --- | --- |
| 调度编排模式（dispatch-orchestrator） | 三阶段、11 个步骤及对应理解/证据，持续记录需求和待办变化 |
| 任意其他预设 | 对话开始一次多层对照，返回理解；完成后状态栏仅显示“已经编排”，无三阶段待办/验收流程 |

普通预设先通过 relic_prepare 读取当前公开注册能力，再用 relic_result 提交理解并向用户说明。尚未收到真实理解时显示“多层对照”，不会提前声称已完成。后续输入不重复启动对照。切换预设时以当前宿主选择为准；套件不修改其他插件的调度模式。

## 调度编排模式

| 阶段 | 步骤 |
| --- | --- |
| 1 · 规划 | 原始提示词理解 → 任务分诊 → 工具/验证/团队/身份四层对照 → 第三方评价 → 综合装配规划 |
| 2 · 执行反应 | 补充需求评估 → 待办增量与覆盖判断 → 执行与认识沉淀 |
| 3 · 验证交付 | 全链路对照 → 验证器验收与交付结论 → 项目缺项、问题及套件反馈 |

每个环节应先查看并提交公开理解，建议可不采纳但须解释依据。状态栏显示阶段和当前步骤，展开后查看完整框图、步骤状态、报告和证据。未评估、已评估无变化、修改、失败分别呈现，不伪造通过。

- dispatch_plan 理解输入并分诊；dispatch_review 调用已挂载验证器的公开工具；dispatch_commit 结合真实评价提交任务认识、计划和初始待办，进入系统上下文与进度。
- dispatch_adjust 评估用户补充；dispatch_refine 沉淀执行中深入的认识，增量修改待办/计划；dispatch_checkpoint 重读依据。重复需求保留记录，不重复新增工作。
- dispatch_delivery 对照原始/补充需求和实际结果，并尝试 verifier_current_session；dispatch_conclude 提交完成内容、实现、整体效果与限制。模型需向用户汇报；系统上下文不是自动生成的可见聊天消息。
- dispatch_report 记录阶段理解和静态/动态身份；dispatch_export 保留原始和过程输入、计划、待办历史与建设反馈。进程内记录可跨轮次保留，重启前可导出。

## 与其他插件共用

套件只注册自己的工具、路由、看板和预设。不注册第二个计划模式或委派引擎，不添加工具拒绝列表，不修改任何外部插件。团队、记忆、技能、MCP、角色和其他插件工具按宿主和当前预设规则使用。多层对照发现能力不等于已调用成功。

dsh-llm-verifier 保持独立：看板只设置本任务规划工具路由和重复次数，实际裁判模型由原验证器配置/返回决定。未注册、失败、取消和过期据实记录；评分不自动等于验收通过。

## 3.0.3 界面修复

每个挂载入口持有自己的样式，避免旧挂载卸载时删除活跃样式。控件使用明确样式、单行截断和响应式宽度；详情浮层固定在视口内。没有增加 Rust 或额外进程：此修复针对样式生命周期和布局，而非计算性能。

## 安装与开发

Node.js ≥22.19；DSH >=0.2.1-0 <0.3。发行包包含构建依赖；源码安装依赖后运行：

~~~sh
npm install
npm run verify
node scripts/pack.mjs <output-directory>
~~~

从仓库开发时进入 main/；发行包根目录就是插件目录。按 DSH 的本地 bundle 流程安装。升级脚本只覆盖本套件发布文件并保留现有配置和回滚备份，详见 [部署说明](DEPLOYMENT.md)。CLI 组合、夹具和磁盘安装不能替代真实宿主应用确认；替换已安装 JavaScript 后依宿主流程重新加载并核对版本。
