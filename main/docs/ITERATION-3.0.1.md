# Orchestrator Suite 3.0.1 修复记录

用户指出：引导指执行方式可变，不是直接不做环节；需要有序查看步骤、表达理解、评估补充与待办，且交付验收必须尝试。这是使用智能体开展项目的方法，不是强制开发项目的实施步骤。

## 根因与修复

| 根因 | 修复 |
| --- | --- |
| 短输入创建进度时把规划步骤标成 skipped | full/light 只控制评估篇幅，两者均保留查看与理解环节；系统也读取短任务注册清单 |
| dispatch_context 和 dispatch_commit 可无验证直接装配 | 缺少理解返回 needs-assessment；未尝试规划验证时实际补尝试，返回结果供模型阅读，提交 reviewUnderstanding 后才完成装配 |
| 待办无变化被当成无需处理，无法知道是否评估 | 独立 todoAssessments；dispatch_todo_assess 记录理解、原因与覆盖依据；无变更明确显示，不增加变更历史 |
| 重复输入由字符串比较自动标已评估 | 只提供 duplicateOf 线索，仍等待模型逐条查看与影响评估 |
| dispatch_delivery 不调用交付验收 | 提交交付报告时实际尝试 verifier_current_session，成功、失败、不可用、取消和过期都有记录 |
| 旧次理解可能当成新次评价已理解 | 每次验证有独立 ID，理解关联本次已结束尝试；调用前和旧次理解不充当本次理解 |
| 只有页面版本，无法确认宿主加载哪个入口 | 进度与看板公共接口返回运行版本；状态栏显示版本与不一致提示 |

规划与交付第三方机制保持原接口、参数与内部配置，结果无论好坏都要展示。工具注册不可用不伪称实际调用，低分不宣称通过。无变更评估与变更历史分开，避免循环修改待办和重走初始规划。

模型可以调整、不采纳执行建议，但不能用“非强制”直接略过查看和说明。框架不会通过代码制造模型理解，也不能保证完全忽视规范的模型遵守所有步骤；此时显示准确的未评估缺口。

验证结果见 RELEASE-SUMMARY.json；真实宿主配置组合、磁盘安装、运行生效与 GUI/裁判真实调用是不同证据。自动测试中的验证器响应为夹具，不是实际第三方结果。任务记录仍不跨宿主重启自动恢复。
